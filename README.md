# Saga CQRS Orchestrator — Go, RabbitMQ и PostgreSQL

Практический пример микросервисной архитектуры на **Go**, показывающий, как организовать распределённый бизнес-процесс без использования тяжёлых распределённых транзакций.

Проект можно использовать как **учебный стенд, reference implementation или основу для собственного микросервисного сервиса**, где несколько компонентов должны согласованно выполнять одну бизнес-операцию.

## Что вы получите, изучив проект

Репозиторий позволяет не просто посмотреть на набор технологий, а увидеть, **как они работают вместе в реальном сценарии**:

* как создавать распределённый бизнес-процесс с помощью **Saga Orchestration**;
* как разделять операции изменения и чтения данных через **CQRS**;
* как организовать асинхронное взаимодействие сервисов через **RabbitMQ**;
* как хранить состояние бизнес-операции в **PostgreSQL**;
* как реализовать **Eventual Consistency**;
* как обрабатывать успешное завершение и изменение состояния заказа;
* как связать HTTP API, очередь сообщений и базу данных в единый процесс;
* как запускать инфраструктуру локально через **Docker Compose**;
* как автоматизировать типовые команды проекта с помощью **Makefile**.

Проект особенно полезен разработчикам Go, которые хотят перейти от отдельных HTTP-сервисов к пониманию **асинхронных взаимодействий и распределённых бизнес-процессов**.

---

## Какую проблему решает проект

В микросервисной архитектуре одна бизнес-операция может затрагивать несколько независимых компонентов.

Например:

```text
Создание заказа
      │
      ▼
  Order Service
      │
      ▼
   RabbitMQ
      │
      ▼
  Warehouse
      │
      ▼
результат операции
      │
      ▼
Saga Orchestrator
      │
      ├── успех ──────► COMPLETED
      │
      └── ошибка ─────► REJECTED
```

Вместо попытки выполнить одну большую распределённую транзакцию система разбивает процесс на последовательность локальных операций.

**Saga Orchestrator** координирует этот процесс и переводит заказ между состояниями.

Это позволяет увидеть на практике, как строятся системы, где отдельные компоненты могут работать независимо, а согласованность достигается через события и управление состоянием.

## Архитектура

Проект демонстрирует взаимодействие нескольких основных компонентов.

### 1. Command Side

HTTP-запрос создаёт новый заказ.

Заказ сохраняется в PostgreSQL со статусом:

```text
PENDING
```

После этого запускается дальнейшая обработка бизнес-процесса.

### 2. RabbitMQ

RabbitMQ используется как транспорт для асинхронного обмена событиями между компонентами.

Через очереди можно увидеть принцип взаимодействия:

```text
Producer → Queue → Consumer
```

Это позволяет отделить отправителя сообщения от компонента, который его обрабатывает.

### 3. Saga Orchestrator

Оркестратор является центральной частью демонстрации.

Он получает результаты операций и определяет дальнейшее состояние заказа:

```text
PENDING
   │
   ├── операция успешна
   │        ↓
   │   COMPLETED
   │
   └── операция не выполнена
            ↓
        REJECTED
```

Таким образом, бизнес-процесс не зависит от одной общей транзакции между всеми компонентами.

### 4. Query Side

Состояние заказа можно получить отдельно от процесса его изменения.

Это демонстрирует базовый принцип **CQRS**:

```text
Command → изменение состояния

Query → получение состояния
```

## Что можно изучить на примере

### Saga Pattern

Увидеть, как организуется распределённая операция, состоящая из нескольких локальных шагов.

### CQRS

Понять практический смысл разделения команд и запросов и увидеть, как состояние системы может изменяться и читаться разными путями.

### Eventual Consistency

Разобраться, почему в распределённых системах состояние компонентов может изменяться не одновременно и как система приходит к согласованному состоянию через обмен событиями.

### Message Broker

Посмотреть полный цикл работы с RabbitMQ:

```text
создание сообщения
       ↓
публикация
       ↓
очередь
       ↓
получение
       ↓
обработка
       ↓
изменение состояния
```

### Docker

Получить готовую локальную инфраструктуру, которую можно поднять без ручной установки PostgreSQL и RabbitMQ.

## Быстрый запуск

### 1. Запустить инфраструктуру

```bash
make up
```

Или:

```bash
docker-compose up -d
```

Будут запущены необходимые компоненты, включая PostgreSQL и RabbitMQ.

### 2. Инициализировать базу данных

```bash
make db-init
```

Либо вручную:

```bash
docker exec -i dio_db_orders \
  psql -U dio_admin -d orders_db < scripts/init.sql
```

### 3. Запустить Go-приложение

```bash
make run
```

Или:

```bash
go run cmd/server/main.go
```

После запуска API доступен на:

```text
http://localhost:8080
```

## Работа с RabbitMQ

После запуска RabbitMQ доступна административная панель:

```text
http://localhost:15672
```

Стандартные учётные данные для локального запуска:

```text
Login: guest
Password: guest
```

В интерфейсе RabbitMQ можно наблюдать очереди и сообщения, которые используются приложением.

## Создание заказа

Создать заказ можно через HTTP API:

```bash
curl -X POST http://localhost:8080/orders
```

Пример ответа:

```json
{
  "id": "6983d6d9-25de-4e87-be12-34fb76cf1194",
  "status": "PENDING"
}
```

На этом этапе заказ создан, но распределённый процесс ещё не завершён.

После обработки Saga состояние заказа изменяется:

```text
PENDING → COMPLETED
```

---

## Проверка состояния заказа

Получить текущее состояние можно через API:

```bash
curl -X POST \
  "http://localhost:8080/status?id=6983d6d9-25de-4e87-be12-34fb76cf1194"
```

Пример:

```json
{
  "id": "6983d6d9-25de-4e87-be12-34fb76cf1194",
  "status": "COMPLETED"
}
```

Таким образом можно проследить полный жизненный цикл операции:

```text
HTTP Request
     ↓
Create Order
     ↓
PostgreSQL
     ↓
PENDING
     ↓
RabbitMQ
     ↓
Saga Orchestrator
     ↓
COMPLETED / REJECTED
```
